# DDA: Blazor and C#

## Structure and state

- Follow the configured Blazor Web App mode. The class material uses .NET 10, Interactive Server, and global interactivity; verify the repository before applying those exact settings.
- Put routable views under `Components/Pages`, layout under `Components/Layout`, and reusable UI under `Components` or a feature-local component folder.
- A page receives input, renders state, handles UI events, and calls a service. A service owns CRUD/data logic and its collection.
- Register services in `Program.cs` and inject them with `@inject` or constructor injection. Prefer scoped lifetime for class-style application services; justify any singleton because it shares state across users.
- Let the service assign identifiers. Return a small explicit result such as `bool` when the caller only needs success/failure.

## Forms and validation

- Put `DataAnnotations` on the input model.
- Use `EditForm`, `DataAnnotationsValidator`, Blazor input components, `@bind-Value`, and a `ValidationMessage` for every important field.
- Handle valid submission with `OnValidSubmit`.
- Do not combine `@bind` and `@oninput` for the same event.
- Pass an event method without parentheses. Use a lambda only when the event must carry a value or other context.

See `../assets/blazor-form-pattern.razor` for a minimal pattern.

## Collections and editing

- Prefer LINQ (`Where`, `Select`, `OrderBy`, `FirstOrDefault`, `Any`) and materialize with `ToList()` when a snapshot is required.
- Handle the possible `null` from `FirstOrDefault`.
- Copy an object before adding it to a collection or editing it in a form. Do not bind an edit form directly to the stored object when cancel must preserve the original.

## Review checks

- No `new SomeService()` inside a Razor component.
- UI code does not own CRUD storage rules.
- Validation is visible next to the relevant field.
- IDs and persistence decisions are not generated by the page.
- Events and binding use one clear mechanism.
